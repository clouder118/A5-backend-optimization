# 旅行手账共创 PRD

- 状态：TJ-01～TJ-06 全部完成
- 任务类型：本地 Markdown
- 产品范围：A5 灵山胜境游客端 `/travel-journal` 与评论社区 `/community`
- 目标终端：PC 端
- 开发门禁：只有用户明确说“开始开发”后才能实施
- 实施原则：仅实现本文范围，遵循 `karpathy-guidelines`
- 任务标签：`ready-for-agent`

## Problem Statement / 问题陈述

当前游客端能够浏览景点、使用数字人导游和在评论社区发表短文字留言，但缺少把旅途照片、即时心情和游览感受整理为完整旅行记录的能力。游客需要自行组织文章结构、撰写图片说明并完成排版，普通评论最多 500 字且只能展示纯文字，无法承载一篇接近微信公众号旅行推文的长篇图文内容。

旅行中的照片与感受具有强时效性。若游客离开产品后再整理，创作意愿和素材上下文容易流失。本功能需要让游客在产品内上传最多 9 张旅行照片或只填写文字，通过 Kimi K3 一次性理解全部素材并生成一篇图文对应、可继续编辑的旅行手账。游客确认后可以把完整手账发布到评论社区，也可以导出为 PDF 留存。

本功能还需要解决草稿持久化、图片隐私处理、社区长图文展示、发布快照、删除联动和模型失败恢复等问题，同时保持现有普通评论、数字人导游和其他游客端功能不变。

## Solution / 解决方案

在游客端侧边栏“评论社区”下方新增“旅行手账共创”入口，路由为 `/travel-journal`，仅对已登录游客开放。

页面提供“共创手账”和“我的手账”两个标签页：

- “共创手账”用于上传图片、输入旅途描述、选择目标字数、调用 Kimi K3、编辑固定结构的图文内容并实时预览。
- “我的手账”用于查看多篇草稿和已发布手账，并执行继续编辑、复制为新草稿、PDF 导出和删除。

游客可以上传 0–9 张图片，也可以完全不上传图片，仅凭文字创作。图片与文字至少提供一项。图片上传后经过格式、大小和数量校验，服务端移除 EXIF 等隐私元数据，生成展示副本与更小的模型识别副本，不长期保留原始文件。

创作时把当前全部图片、游客描述和目标字数一次性提交给 `kimi-k3`。模型使用 `reasoning_effort="low"`，通过严格 JSON Schema 返回总标题、开场、每张图片对应的小标题与讲述段落、结尾。模型结果回填编辑器并自动保存为草稿，不自动发布、跳转或导出。

发布时把手账作为新的“旅行手账”社区帖子类型立即公开。评论社区列表展示封面、标题和摘要，点击后在当前页面的大尺寸弹窗中阅读完整图文内容。普通文字评论继续沿用现有结构和 500 字限制。

PDF 由后端生成，包含标题、游客昵称、创作日期、完整图文内容和低调产品标识，不包含账号 ID、定位元数据或社区互动数据。

## User Stories / 用户故事

1. 作为已登录游客，我希望在侧边栏“评论社区”下方看到“旅行手账共创”，以便快速进入旅行记录功能。
2. 作为未登录游客，我希望该页面继续遵循游客端现有登录保护规则，以便账号草稿和图片不会混淆。
3. 作为游客，我希望通过 `/travel-journal` 直接访问共创页面，以便保存和分享明确的页面入口。
4. 作为游客，我希望在“共创手账”和“我的手账”之间切换，以便区分当前创作与历史管理。
5. 作为游客，我希望点击选择多张旅行照片，以便一次加入当天素材。
6. 作为游客，我希望拖拽照片到上传区域，以便快速添加本地图片。
7. 作为游客，我希望一次多选图片，以便减少重复操作。
8. 作为游客，我希望单篇最多上传 9 张图片，以便控制内容长度和生成等待时间。
9. 作为游客，我希望可以不上传图片，只填写旅行感受生成纯文字手账，以便没有合适照片时仍能创作。
10. 作为游客，我希望可以只上传图片而不填写文字，以便由模型根据照片内容组织旅行故事。
11. 作为游客，我希望图片和文字至少提供一项，以便系统不会在没有素材时生成无依据内容。
12. 作为游客，我希望上传 JPG、PNG 或 WebP 图片，以便使用常见旅行照片格式。
13. 作为游客，我希望单张图片不超过 10 MB，以便上传失败时获得明确限制说明。
14. 作为游客，我希望看到图片缩略图和顺序编号，以便确认素材是否正确。

16. 作为游客，我希望拖动调整照片顺序，以便控制文章叙事顺序。
17. 作为游客，我希望上传照片中的定位等 EXIF 信息不会被长期保存或公开，以便保护隐私。
18. 作为游客，我希望展示图片仍保持适合阅读和 PDF 留存的清晰度，以便隐私处理不会明显损害观感。

## Implementation Decisions / 实施决策

### 路由与导航

- 新增游客端受保护路由 `/travel-journal`。
- 侧边栏名称为“旅行手账共创”，位于“评论社区”正下方。
- 沿用现有游客认证、布局和视觉语言，不新增另一套登录或导航机制。
- 本期仅保证 PC 端布局，不增加移动端专项适配。

### 页面结构

- 页面顶部提供“共创手账”和“我的手账”两个标签页。
- “共创手账”上方为素材与生成设置区，下方为左侧分段编辑、右侧公众号式实时预览的双栏区。
- “我的手账”以卡片列表展示草稿和已发布内容。
- 生成前允许编辑素材、图片顺序、描述和目标字数。
- 生成后编辑器保持固定结构，不提供通用富文本工具栏。

### 输入约束

- 图片允许 0–9 张，格式仅限 JPEG、PNG、WebP，单张最大 10 MB。
- 文字描述最大 2000 个字符。
- 图片和文字至少提供一项；两者都为空时禁止生成。
- 字数预设为 300、600、1000、1500，默认 600。
- 自定义字数必须为 200–3000 的整数。
- 目标字数作为 Prompt 中的正文篇幅参考，不做后端字数硬校验；总标题和图片说明不计入目标字数。

### 图片资产处理

- 图片通过后端接收和校验，前端不直接把长期访问凭证或服务器路径写入数据。
- 上传后生成最长边不超过 2560px 的高质量展示副本，并移除 EXIF 等元数据。
- 另生成更小的模型识别副本，用于控制 Kimi 请求体大小和视觉 token 消耗。
- 原始上传文件处理完成后不长期保存。
- 草稿图片只允许所属游客访问；社区发布后由受控资源接口提供公开展示。
- 删除草稿时清理不再被其他有效记录引用的图片。

### 手账数据模型

- 手账是独立领域对象，至少包含游客归属、状态、素材描述、目标字数、标题、开场、图片段落、结尾、创建时间和更新时间。
- 状态至少区分 `draft` 与 `published`。
- 图片记录包含稳定标识、展示资源、模型资源、排序和对应讲述内容。
- 账号之间严格隔离；游客只能读取、编辑、复制、导出和删除自己的手账。
- 生成或编辑后自动保存当前草稿。
- 已发布手账不可直接编辑；继续创作通过“复制为新草稿”完成。

### Kimi K3 共创

- 旅行手账使用独立 Kimi 配置，不复用数字人 MiMo 客户端。
- API 使用 OpenAI 兼容的 Chat Completions，模型名为 `kimi-k3`。
- API Key 只从后端环境变量 `MOONSHOT_API_KEY` 读取，不进入前端、PRD、Issues、日志或版本库。
- 一次请求提交当前全部模型图片副本、游客描述、目标字数和图片顺序。
- 请求使用 `reasoning_effort="low"`。
- 请求体必须保持在 Kimi 视觉接口的 100 MB 限制内。
- 使用严格 JSON Schema 约束最终结果，返回总标题、开场、图片标识对应的段落和结尾。
- 只解析最终内容，不向游客展示模型思考内容。
- 每张图片必须且只对应一个图片段落，后端校验图片标识完整性和唯一性；目标字数仅进入 Prompt，不作为响应拒绝条件。
- 模型失败、响应非法或内容不完整时返回可理解错误并保留草稿，不切换 MiMo，不生成本地模拟文章。
- AI 可以润色情绪和氛围，但不得编造具体同行人物、行程事件、景区历史、票价、开放时间或安全信息。

### 固定结构编辑

- 可编辑字段为总标题、开场、每张图片的小标题与讲述、结尾。
- 不支持新增、删除或重排纯文字段落。
- 图片与对应讲述作为整体排序或删除。
- 生成后新增图片时创建空讲述区域，不自动调用模型。
- 已有编辑内容再次生成前必须确认覆盖。
- 生成结果自动保存为草稿，但不自动发布、跳转或导出。

### 草稿与生命周期

- 支持每位游客保存多篇手账。
- “我的手账”支持分页或等价的增量加载，避免一次加载所有记录。
- 草稿支持继续编辑、删除、生成、发布和导出。
- 已发布手账支持查看、复制为新草稿、导出和删除。
- 自动保存采用防抖或等价机制，保存中、保存成功和保存失败状态必须可见。
- 删除操作必须二次确认。

### 社区发布

- 扩展社区帖子类型，新增旅行手账类型；普通评论数据和 500 字规则保持不变。
- 发布前显示公开范围确认。
- 发布在一个一致性操作中创建社区帖子并更新手账状态，避免只完成一半。
- 社区旅行手账卡片包含封面、标题、摘要、作者、时间和现有点赞等公共信息。
- 点击卡片在 `/community` 当前页面打开大尺寸纵向图文阅读弹窗，不新增详情路由。
- 发布成功后跳转到 `/community`，根据新帖子标识定位并高亮。
- 已发布内容作为快照，不随之后的新草稿编辑变化。
- 删除已发布手账时同步软删除社区帖子。
- 游客在社区删除旅行手账帖子后，手账保留内容并回到未发布草稿状态。
- 旅行手账继续受现有管理员隐藏、恢复或等价社区治理能力约束。

### PDF 导出

- PDF 由后端根据当前已保存手账生成并以附件响应下载。
- 支持纵向多页排版，包含总标题、游客昵称、创作日期、开场、图片段落、结尾和低调产品标识。
- 不包含账号 ID、EXIF、定位、点赞数、社区状态等无关信息。
- 文件名由安全处理后的手账标题与日期组成。
- 使用 Pillow 完成图片处理，使用 ReportLab 完成中文 PDF 生成；这两个后端依赖已获得用户批准。

### 失败与恢复

- 图片上传失败只影响对应文件，已经成功的素材和草稿继续保留。
- 重复点击生成、发布和导出时必须防止并发重复提交。
- Kimi 未配置、超时、拒绝或返回非法结构时显示明确错误与重试入口。
- 发布失败不改变草稿状态。
- PDF 失败不改变手账和社区数据。
- 所有失败状态不得清空游客已输入文字或已上传图片。

### 安全与隐私

- 服务端验证文件 MIME、扩展名、实际解码结果、单张大小、总数量和资源归属。
- 文件名和存储路径由服务端生成，不使用游客原始文件名作为路径。
- 上传内容和游客描述视为不可信输入，不能覆盖系统安全指令或要求泄露密钥。
- API Key 不得出现在客户端构建、接口响应、错误详情和日志中。
- 社区公开资源与草稿私有资源使用不同授权规则。

### 主要模块

1. 手账素材模块：上传、校验、隐私处理、副本生成和顺序管理。
2. Kimi K3 共创模块：多图请求、严格结构化输出和失败处理。
3. 手账生命周期模块：草稿、自动保存、列表、复制、发布状态和游客隔离。
4. 社区发布模块：旅行手账帖子、发布联动、删除联动和阅读弹窗。
5. PDF 导出模块：中文图文排版和文件下载。
6. PC 端共创界面模块：路由、导航、素材输入、固定结构编辑、实时预览和我的手账。

## Testing Decisions / 测试决策

### 测试原则

- 自动化测试验证外部可观察行为，不绑定私有函数、内部类名或具体代码组织。
- 自动化测试不得调用真实 Kimi API，也不得读取真实 `MOONSHOT_API_KEY`。
- Kimi 测试使用可控 HTTP 传输或等价替身，验证请求结构、响应解析和错误恢复。
- 文件测试使用临时目录和临时数据库，不污染本机正式素材与数据。
- 现有普通社区帖子测试必须继续通过，证明兼容性未被破坏。

### 后端测试范围

- 只有已登录游客可以创建和管理手账。
- 不同游客之间无法读取、修改、导出或删除对方手账。
- 0–9 张图片规则、格式、单张 10 MB、文字 2000 字和字数 200–3000 校验。
- 图片解码、EXIF 移除、展示副本和模型副本生成。
- 纯文字、纯图片和图文混合三种创作请求。
- Kimi 请求使用 `kimi-k3`、`reasoning_effort="low"`，并包含全部图片与文本。
- 严格结构化结果的成功解析、缺图、重复图、非法 JSON、超时和拒绝处理。
- 生成结果保存草稿但不自动发布。
- 草稿自动保存、列表、复制、删除和状态转换。
- 发布手账与创建社区帖子的一致性。
- 删除已发布手账与社区帖子联动。
- 社区删除后手账回到未发布草稿。
- 普通评论仍执行原有 500 字纯文字行为。
- PDF 响应类型、文件名、PDF 文件头、中文正文和图片排版基本完整性。

### 前端测试范围

- 导航入口位置和 `/travel-journal` 登录保护。
- 纯文字创作、图片上传、多选、拖拽、排序、删除和 9 张上限。
- 预设字数、自定义字数和输入校验。
- 生成加载、失败重试、覆盖确认和素材保留。
- 固定结构编辑、图片段落整体排序、生成后新增图片空段落。
- 自动保存状态、刷新恢复、多篇草稿列表。
- 发布确认、发布成功跳转、高亮和失败保留。
- 社区旅行手账卡片、完整阅读弹窗和普通评论兼容。
- 已发布复制为草稿、删除联动。
- PDF 下载入口和浏览器收到下载文件。

### 真实联调

- 开发完成并由用户提供本机环境配置后，执行一次受控 Kimi K3 联调。
- 联调覆盖 0 张、1 张和 9 张图片中的代表场景，重点观察请求大小、等待时间、图文对应和目标字数。
- 联调不会把 API Key 输出到终端、测试报告或提交内容。

## Out of Scope / 非目标

- 移动端专项适配。
- 手机摄像头拍摄。
- 视频上传或视频理解。
- JPEG、PNG、WebP 以外的上传格式。
- 任意字体、颜色、字号、对齐和自由拖拽富文本排版。
- 新增、删除或重排纯文字段落。
- 直接覆盖编辑已经发布到社区的手账。
- MiMo 或本地模拟内容作为 Kimi 失败时的替代生成结果。
- PDF 以外的 Word、HTML、长图或其他导出格式。
- 微信、微博或其他第三方平台的直接分享与授权。
- 新增社区详情路由。
- 重做普通评论的数据结构、发布入口和展示方式。
- 基于 EXIF 定位自动生成路线。
- 自动识别人脸、人物身份或同行关系。
- 云对象存储、CDN、多机共享文件系统和生产级资源迁移。
- 手账模板商城、主题皮肤、协同编辑、版本历史和公开编辑。
- 未经用户明确“开始开发”即实施功能代码。

## Further Notes / 补充说明

- Kimi K3 官方文档说明模型支持视觉输入、OpenAI 兼容 Chat Completions、严格结构化输出和 `reasoning_effort`；图片数量没有模型侧硬限制，但请求 Body 不得超过 100 MB。
- Kimi 视觉输入不使用公网图片 URL；本功能使用后端生成的模型副本转为 Base64 内容提交。
- Kimi API 基础地址与模型名通过后端配置集中管理，避免散落在业务代码中。
- 本机当前尚未配置 `MOONSHOT_API_KEY`。开发开始后仅写入被 Git 忽略的本地环境文件；文档和仓库只记录变量名。
- 用户在对话中提供过密钥值，该值不得复制到本文、Issues、代码、测试、日志或提交中；正式部署前建议重新生成。
- 该功能需要对现有社区模型做兼容扩展，但普通评论接口与展示行为必须保持向后兼容。
- PRD 发布后仍需按 `to-issues` 流程确认垂直切片，用户批准 Issues 后进入“等待开始开发”状态。
