# 游客端与管理端端口分离及登录注册 PRD

Status: ready-for-agent

## Problem Statement

当前游客端和管理后台运行在同一个前端入口下，游客页面顶部存在进入后台管理的入口。对于面向演示和后续产品化的“灵山胜境 AI 数字人导览”系统来说，这会让游客体验和运营后台边界不清晰，也不利于后续做真实账号、权限控制和独立部署。

本次开发需要在现有 React + Vite + Ant Design + FastAPI + SQLite 架构基础上，将游客端和管理端拆成两个本地入口端口，并补齐第一版真实后端登录注册能力。游客端支持普通游客注册和登录；管理端支持管理员登录，但不开放管理员注册。UI 风格需要与现有暗色、括号化、景区导览风格保持一致。

## Solution

使用一个代码库、一个前端项目、一个后端服务，但启动两个本地前端入口：

- 游客端：http://127.0.0.1:5173/
- 管理端：http://127.0.0.1:5174/
- 后端 API：http://127.0.0.1:8001/

游客端不再显示或承载后台管理入口。未登录游客可以进入 HOME 首页，但只能看到 HOME、登录和注册入口；未登录时不开放 SPOTS、ROUTES、GUIDE 等功能导航和功能页面。游客注册只需要用户名和密码，注册成功后自动登录并进入游客 HOME。登录后游客端恢复当前完整功能，包含 HOME、SPOTS、ROUTES、GUIDE，并显示用户名和退出登录。

管理端通过独立端口进入。访问 http://127.0.0.1:5174/ 时先进入管理端登录页，管理员登录成功后进入管理后台 dashboard。管理端不提供注册入口。后端启动时自动创建默认管理员账号，默认用户名为 admin，默认密码为 123456。管理员账号只在不存在时创建，不在每次启动时覆盖已有密码。

认证需要是真实后端登录，不做纯前端演示登录。后端新增统一用户表，保存密码哈希，签发 Bearer token。游客端和管理端分别保存 token，互不混用。管理后台相关 API 需要管理员 token。游客端受保护功能需要游客 token；HOME 所需摘要数据可以公开。

日常启动仍保持简单：

- cd frontend && npm run dev：同时启动游客端 5173 和管理端 5174。
- cd frontend && npm run build：一次完成游客端和管理端构建。
- START-HERE.bat：同时启动后端 8001、游客端 5173、管理端 5174。
- stop-local.bat：停止上述服务。

## User Stories

1. 作为未登录游客，我想打开 http://127.0.0.1:5173/ 看到景区 HOME 首页，所以我能先了解“灵山胜境 AI 数字人导览”产品。
2. 作为未登录游客，我只想看到 HOME、LOGIN、REGISTER 入口，所以我不会误以为其他功能已经可用。
3. 作为未登录游客，我不想看到 SPOTS、ROUTES、GUIDE 和 OPS 入口，所以游客端和管理端边界更清晰。
4. 作为未登录游客，我访问 /spots、/routes、/guide 时应回到 HOME，所以未授权功能不会被绕过。
5. 作为未登录游客，我想从 HOME 进入登录页，所以我可以继续使用完整游客功能。
6. 作为未登录游客，我想从 HOME 进入注册页，所以我可以创建第一版游客账号。
7. 作为游客，我想用用户名和密码完成注册，所以注册流程足够简单。
8. 作为游客，我注册成功后想自动登录并进入 HOME，所以我不需要再手动登录一次。
9. 作为游客，我想注册时看到用户名重复、格式不合法、密码过短等错误提示，所以我知道如何修正输入。
10. 作为游客，我想用用户名和密码登录，所以我可以恢复自己的访问状态。
11. 作为已登录游客，我想看到 HOME、SPOTS、ROUTES、GUIDE 导航，所以我能使用当前游客端完整功能。
12. 作为已登录游客，我不想在顶部看到 OPS 管理入口，所以游客端不会暴露后台入口。
13. 作为已登录游客，我想在顶部看到自己的用户名，所以我知道当前登录身份。
14. 作为已登录游客，我想点击 LOG OUT 退出，所以我可以清除当前登录状态。
15. 作为已登录游客，我退出后应回到未登录 HOME 状态，所以界面与权限恢复一致。
16. 作为游客，我想景点列表、景点详情、路线推荐、AI 导游问答在登录后保持原有功能，所以此次认证改造不破坏现有演示链路。
17. 作为游客，我想 AI 导游问答和语音播放继续可用，所以登录改造不会影响数字人导览体验。
18. 作为游客，我想登录页和注册页在手机端也可正常使用，所以移动端演示不会出现横向滚动或遮挡。
19. 作为管理员，我想打开 http://127.0.0.1:5174/ 直接进入管理端登录页，所以后台入口和游客入口完全分离。
20. 作为管理员，我想使用管理员账号登录后台，所以后台访问不再依赖游客端入口。
21. 作为管理员，我不需要在管理端看到注册入口，所以管理员账号创建流程受控。
22. 作为管理员，我登录成功后进入 dashboard，所以我能开始管理景点、路线、知识库和日志。
23. 作为管理员，我想管理端内部使用 /dashboard、/spots、/routes、/knowledge、/logs 这类根级路由，所以独立端口地址更清晰。
24. 作为管理员，我访问旧的游客端 /admin 路径时不应进入后台，所以后台只能从 5174 端口进入。
25. 作为管理员，我想退出登录后回到管理端登录页，所以后台 token 能被明确清除。
26. 作为管理员，我希望管理后台接口真正校验管理员 token，所以登录页不是装饰性的门面。
27. 作为后端开发者，我想用统一用户表区分 visitor 和 admin，所以账号和权限模型简单可扩展。
28. 作为后端开发者，我想保存密码哈希而非明文，所以账号数据满足基本安全要求。
29. 作为后端开发者，我想后端启动时自动创建默认管理员账号，所以本地演示无需手工插入管理员。
30. 作为后端开发者，我想默认管理员只在不存在时创建，所以后续修改密码不会被启动流程覆盖。
31. 作为前端开发者，我想游客 token 和管理员 token 分开保存，所以两个入口不会混用身份。
32. 作为前端开发者，我想 token 无效时自动清理登录态，所以界面不会停留在错误授权状态。
33. 作为演示操作者，我想继续使用 npm run dev 一次启动两个前端入口，所以日常操作保持简单。
34. 作为演示操作者，我想继续使用 START-HERE.bat 一键启动全部服务，所以稳定演示流程不增加复杂度。
35. 作为测试者，我想用明确的登录、注册、未登录访问、管理端访问流程验证此次改造，所以可以快速确认端口分离和权限生效。

## Implementation Decisions

- 使用一个前端代码库和一个后端代码库，不拆成两个独立项目。
- 游客端开发入口为 5173，管理端开发入口为 5174。
- 游客端 5173 不再承载 /admin 相关页面；手动访问 /admin* 时回到游客端 HOME 或游客端兜底页。
- 管理端 5174 使用独立应用入口，未登录时显示管理端登录页。
- 管理端内部路由使用 /dashboard、/spots、/routes、/knowledge、/logs。
- 可保留旧 /admin/* 到新管理端路由的兼容重定向，但 5173 上不得进入后台。
- 游客端未登录时允许访问 HOME，并展示真实或摘要数据。
- 游客端未登录时顶部只保留 HOME，并提供 LOGIN、REGISTER 入口。
- 游客端未登录时隐藏 SPOTS、ROUTES、GUIDE、OPS 导航。
- 游客端未登录时 HOME 中原本进入功能页的按钮应隐藏或替换为登录/注册引导。
- 游客端登录后恢复 HOME、SPOTS、ROUTES、GUIDE 导航。
- 游客端登录后显示 username 和 LOG OUT。
- 游客端不再显示 OPS 管理入口。
- 游客端注册页只包含 username 和 password。
- 游客注册成功后自动登录并跳转游客 HOME。
- 游客注册规则：username 3 到 32 个字符，只允许字母、数字、下划线；password 6 到 64 个字符。
- 游客注册不允许同 role 下用户名重复。
- 管理端不提供管理员注册界面。
- 后端启动时创建默认管理员：admin / 123456。
- 默认管理员密码可由 ADMIN_DEFAULT_PASSWORD 配置覆盖，默认值为 123456。
- 默认管理员用户名可由 ADMIN_DEFAULT_USERNAME 配置覆盖，默认值为 admin。
- 默认管理员只在不存在时创建，不覆盖已有账号。
- 新增统一用户表 app_user，通过 role 区分 visitor 和 admin。
- app_user 至少包含 username、password_hash、role、is_active、created_at、last_login_at 等信息。
- app_user 使用 username + role 唯一约束。
- 后端新增真实认证 API：
  - POST /api/auth/register
  - POST /api/auth/login
  - POST /api/auth/admin/login
  - GET /api/auth/me
- 后端签发 Bearer token，有效期第一版为 7 天。
- 前端游客 token 保存为 a5_visitor_token。
- 前端管理员 token 保存为 a5_admin_token。
- 请求受保护接口时使用 Authorization: Bearer <token>。
- token 无效或过期时返回 401 Unauthorized。
- 游客端 token 无效时清除游客登录态并回到未登录 HOME。
- 管理端 token 无效时清除管理员登录态并回到管理端登录页。
- 管理后台相关接口需要管理员 token，包括 /api/admin/*、/api/knowledge/*、/api/logs/*。
- 保留现有 ADMIN_TOKEN / x-admin-token 兼容能力，供脚本或调试使用；管理端网页使用新 admin Bearer token。
- HOME 所需公开摘要 API 可以不要求游客 token。
- 游客受保护能力包括景点详情、路线推荐、AI 导游问答，以及其他非 HOME 核心功能。
- 前端页面和组件不得直接调用 fetch；新增认证客户端和 token 注入逻辑应放在 API client 层。
- UI 使用现有 React、Vite、TypeScript、Ant Design、Ant Design Icons 和全局样式，不引入新 UI 框架。
- 游客登录/注册页采用当前暗色景区导览风格，可使用景区照片背景、括号化按钮和简洁表单。
- 管理端登录页采用暗色运营控制台风格，避免营销式大图堆砌。
- 登录/注册页面必须适配移动端，不能出现横向滚动、表单遮挡或按钮文字溢出。
- npm run dev 保持一个命令，同时启动游客端 5173 和管理端 5174。
- npm run build 保持一个命令，一次完成游客端和管理端构建。
- START-HERE.bat、start-local.*、stop-local.* 需要同步支持后端 8001、游客端 5173、管理端 5174。

## Testing Decisions

- 测试应验证外部行为，不测试实现细节。例如验证未登录访问 /guide 会回到 HOME，而不是断言某个内部 React state 名称。
- 后端认证服务需要测试游客注册、游客登录、管理员登录、重复用户名、密码长度、无效 token、过期/错误 token、默认管理员创建。
- 后端权限依赖需要测试管理接口在无 token、游客 token、管理员 token、旧 x-admin-token 兼容路径下的行为。
- 游客端路由保护需要测试未登录只显示 HOME/LOGIN/REGISTER，且 /spots、/routes、/guide 不可直接访问。
- 游客端登录后需要测试完整导航恢复、用户名显示、退出登录、功能页可访问。
- 管理端路由保护需要测试 5174 未登录显示登录页，登录后进入 dashboard，退出后回到登录页。
- 前端 API client 需要测试或手动验证 Authorization header 被正确带上，游客和管理员 token 不混用。
- 启动脚本需要手动验证 START-HERE.bat 能同时启动 8001、5173、5174，stop-local.bat 能停止对应服务。
- 构建验证至少运行 cd frontend && npm run build。
- 后端验证至少运行 cd backend && python -m pytest -q。
- 前端流程验证优先运行 verify:visitor 和 verify:admin；如脚本尚未覆盖双端口，需要补充或更新脚本。
- 手动验收需要覆盖桌面和移动宽度，确认登录/注册页面、游客 HOME、管理登录页无布局溢出。

## Out of Scope

- 不做个人中心。
- 不做修改密码。
- 不做忘记密码。
- 不做邮箱、手机号、短信验证码或第三方登录。
- 不做管理员注册界面。
- 不做真实 RBAC 角色矩阵，第一版只区分 visitor 和 admin。
- 不做多租户、多景区 SaaS 权限。
- 不更换 React、Vite、Ant Design 或现有前端技术栈。
- 不引入新的数据库或向量数据库。
- 不改变现有后端核心业务路径、RAG 策略、TTS 策略或知识库来源策略。
- 不修改原始 Scenic Area Public Information Package 资料包。
- 不手工编辑 frontend/dist 产物。

## Further Notes

- 本 PRD 以“演示链路稳定”为优先级。游客端和管理端端口分离应提升产品边界，而不能破坏现有 HOME、SPOTS、ROUTES、GUIDE、数字人问答、来源展示、TTS 和后台运营页面。
- 后续实现时，建议优先完成后端认证和权限依赖，再完成前端双入口与路由保护，最后同步启动脚本和验证脚本。
- 如果后续进入准生产阶段，应重新评估 HttpOnly Cookie、刷新 token、密码修改、管理员账号管理、审计日志和更细粒度权限。
